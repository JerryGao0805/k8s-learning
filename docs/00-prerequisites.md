## 🧠 概念：Kubernetes 到底是什么

### 从一个问题开始

假设你写了一个 Web 应用，用 Docker 打成了镜像。在一台服务器上运行它很简单：

```bash
docker run -d -p 80:8080 my-app:v1
```

但到了生产环境，问题就来了：

| 问题 | 只靠 `docker run` 的做法 |
|---|---|
| 一台机器扛不住，要跑 10 个副本、分散在 5 台机器上 | 登录 5 台机器挨个执行？ |
| 半夜某个容器崩了，或者整台机器挂了 | 等人发现、手动重启？ |
| 要发布 v2，并且不能中断服务 | 手动一个一个替换？出了问题怎么回滚？ |
| 10 个副本前面要有负载均衡，副本的 IP 还经常变 | 手动维护 nginx 配置？ |
| 流量高峰要扩容，低谷要缩容 | 人肉盯着监控？ |

**Kubernetes（简称 K8s）就是把这些事情自动化的系统。** 你可以把它理解成"管理一群机器的操作系统"：你不再关心应用跑在哪台机器上，只需要告诉 K8s "我要什么"，它负责实现，并且**一直维持**这个状态。

### 最核心的思想：声明式 + 控制循环

这是整个 K8s 最重要的概念，后面的所有东西都建立在它上面。

**命令式**（传统做法）：告诉系统"做什么"。

> "启动 3 个容器。"（启动完就结束了，后面挂了一个，没人管）

**声明式**（K8s 的做法）：告诉系统"我要什么状态"。

> "我要**始终**有 3 个这样的容器在运行。"

K8s 收到这个"期望状态"之后，会有一个**控制器（controller）**不停地循环执行：

```
        ┌──────────────────────────────────────────┐
        │                                          │
        ▼                                          │
   观察当前状态 ──► 和期望状态比较 ──► 有差距？──是──► 采取行动缩小差距
   （现在有 2 个）   （期望 3 个）        │            （再启动 1 个）
                                        否
                                        │
                                        └──► 什么也不做，继续观察
```

**打个比方：空调的恒温器。** 你设定 26°C（期望状态），恒温器不停地测量室温（当前状态）：高了就制冷，到了就停，又热了再制冷。你不需要说"开 10 分钟制冷"，只需要说"我要 26°C"。

K8s 里有几十个这样的控制器，每个负责一类事情（副本数、节点健康、Service 的后端列表……）。**整个 K8s 本质上就是一个存放"期望状态"的数据库，加上一大群不停干活、让现实向期望靠拢的控制器。** 记住这句话，后面会反复印证。

### 集群的组成

一个 K8s 集群由两类机器组成：

- **Control Plane（控制平面）**：集群的"大脑"，负责决策（存储状态、调度、运行控制器）。生产环境一般 3 台，做高可用。
- **Worker Node（工作节点）**：真正运行你的应用容器的机器。

```
┌─────────────────────── Control Plane（大脑）───────────────────────┐
│                                                                    │
│   ┌──────────┐      ┌───────────────────┐      ┌────────────────┐  │
│   │   etcd   │◄────►│  kube-apiserver   │◄────►│ kube-scheduler │  │
│   │ （档案室）│      │ （唯一的前台）     │      │  （调度员）     │  │
│   └──────────┘      └───────────────────┘      └────────────────┘  │
│                       ▲      ▲                                     │
│                       │      │      ┌──────────────────────────┐   │
│                       │      └─────►│ kube-controller-manager  │   │
│                       │             │  （一群控制器 / 监工）     │   │
│                       │             └──────────────────────────┘   │
└───────────────────────┼────────────────────────────────────────────┘
          所有组件都只跟  │  apiserver 打交道，互相之间不直接通信
┌───────────────────────┼──────── Worker Node（干活的）──────────────┐
│                       ▼                                            │
│   ┌──────────────┐   ┌──────────────┐   ┌───────────────────────┐  │
│   │   kubelet    │──►│  containerd  │──►│ 容器 容器 容器 ...      │  │
│   │（节点上的工头）│   │ （容器运行时）│   └───────────────────────┘  │
│   └──────────────┘   └──────────────┘                              │
│   ┌──────────────┐   ┌──────────────────────┐                      │
│   │  kube-proxy  │   │ CNI 插件（Calico）    │                      │
│   │（流量转发规则）│   │ （给容器接网线）       │                      │
│   └──────────────┘   └──────────────────────┘                      │
└────────────────────────────────────────────────────────────────────┘
```

每个组件一句话（先有个印象，后面每个都会拆开细看）：

| 组件 | 比喻 | 职责 |
|---|---|---|
| **kube-apiserver** | 唯一的前台 | 集群的统一入口。`kubectl`、所有组件都只跟它通信。负责认证、鉴权、校验，再把数据存进 etcd |
| **etcd** | 档案室 | 一个分布式键值数据库，存着集群的全部状态（"期望状态"和"当前状态"）。**它丢了，集群就丢了** |
| **kube-scheduler** | 调度员 | 新建的 Pod 还没分配机器时，由它挑一台最合适的节点（看资源够不够、有没有约束） |
| **kube-controller-manager** | 一群监工 | 运行着那几十个控制器：副本数不够就补、节点失联就处理…… |
| **kubelet** | 节点上的工头 | 每个节点上都有一个。从 apiserver 领到"这台机器该跑哪些 Pod"，然后指挥容器运行时去执行，并上报状态 |
| **containerd** | 工人 | 真正拉镜像、创建和启动容器的程序（容器运行时） |
| **kube-proxy** | 交通警察 | 在每个节点上维护转发规则（iptables），让访问 Service 的流量能找到后端的 Pod |
| **CNI 插件（Calico）** | 网络施工队 | 给每个 Pod 分配 IP、接好网线，让不同机器上的 Pod 能互相通信 |
| **CoreDNS** | 电话簿 | 集群内部的 DNS，让你能用 `my-service` 这样的名字访问服务 |

> 💡 **一个关键事实**：control plane 的组件（apiserver、etcd、scheduler……）在 kubeadm 搭的集群里，**本身也是以容器的形式运行的**，由 kubelet 管理。第 03 章你会亲眼看到这一点。

### 一个最小的例子：创建一个应用时发生了什么

你执行 `kubectl create deployment web --image=nginx --replicas=3`：

```
① kubectl ──► apiserver：  "我要一个叫 web 的 Deployment，3 个副本"
② apiserver ──► etcd：      存下来
③ Deployment 控制器发现：   "有个新 Deployment，但还没有对应的 Pod" → 通过 apiserver 创建 3 个 Pod
④ scheduler 发现：          "有 3 个 Pod 还没分配节点" → 给每个挑一台机器，写回 apiserver
⑤ 各节点的 kubelet 发现：   "有 Pod 分配给我了" → 让 containerd 拉镜像、启动容器，CNI 给它配好网络
⑥ kubelet ──► apiserver：   "Pod 已经 Running"
```

注意：**没有谁"命令"谁**。每个组件都只是盯着 apiserver 里自己关心的那部分数据，发现"现实和期望不一致"就动手。这就是控制循环。第 06 章我们会用命令一步一步观察这个过程。

## 🧠 我们要搭的集群

```
                    你的 Mac
                       │  aws ssm（登录节点、开隧道）
                       ▼
 ┌───────────────── AWS VPC（3 个可用区）─────────────────┐
 │                                                        │
 │  公有子网：  [NAT 实例]   ← 私有子网的机器经它上网       │
 │                                                        │
 │  私有子网：  cp-1  cp-2  cp-3     ← control plane       │
 │             worker-1 worker-2 worker-3                 │
 │                                                        │
 │             [内网 NLB] ← api.k8s.internal:6443          │
 │              （apiserver 的统一入口）                    │
 └────────────────────────────────────────────────────────┘
```

**渐进式搭建**：先用 **1 个 control plane + 2 个 worker** 把集群跑起来，学完核心对象之后（第 11 章），再扩展成 **3 + 3** 的高可用集群。这样每一步都能体会到"为什么需要它"。

几个设计决定和理由：

| 决定 | 理由 |
|---|---|
| 节点放在**私有子网**，没有公网 IP | 生产环境的标准做法：服务器不直接暴露在公网 |
| 用 **SSM** 登录，不开 SSH | 不开放任何入站端口，登录权限由 AWS IAM 控制，还能留审计记录 |
| **自建 NAT 实例**，不用 AWS NAT Gateway | 省钱（NAT Gateway 约 $33/月且不能停机）；顺便学习 Linux 转发和 NAT 原理，后面理解 K8s 网络正好用得上 |
| **Graviton（arm64）**机型 | 比同规格的 x86 便宜约 20% |
| **kubeadm** | K8s 官方的集群搭建工具，每一步都看得见 |

### 步骤 1：让 zsh 支持命令里的注释

文档里的命令有时带 `# 注释`。macOS 默认的 zsh **在交互模式下不认注释**，粘贴带 `#` 的行会报 `command not found: #`。打开这个选项：

💻 **Mac：**

```bash
echo 'setopt interactivecomments' >> ~/.zshrc
source ~/.zshrc
```

### 步骤 2：安装 kubectl v1.37

`kubectl` 是操作 K8s 集群的命令行工具。

先看看你现在用的是哪个 kubectl：

💻 **Mac：**

```bash
which -a kubectl
ls -l "$(which kubectl)"
kubectl version --client
```

你应该会看到它指向 `/Applications/Docker.app/...`，是 **Docker Desktop 自带的 v1.34**。

**为什么要换？** K8s 有个**版本偏差策略**：kubectl 只保证和相差 ±1 个小版本的集群兼容。我们先装 v1.36 的集群，之后升级到 v1.37，所以 kubectl 用 **v1.37** 正好两头都兼容（1.36、1.37、1.38）。

我们把新版本装到 `~/.local/bin`。它在你的 PATH 里排第一，会优先于 Docker 自带的那个；Docker Desktop 本身不受影响。

💻 **Mac：**

```bash
cd /tmp
KUBECTL_VERSION=v1.37.2

curl -fLO "https://dl.k8s.io/release/${KUBECTL_VERSION}/bin/darwin/arm64/kubectl"
curl -fLO "https://dl.k8s.io/release/${KUBECTL_VERSION}/bin/darwin/arm64/kubectl.sha256"

# 校验下载的文件没有被篡改：应该输出 "kubectl: OK"
echo "$(cat kubectl.sha256)  kubectl" | shasum -a 256 --check

chmod +x kubectl
mkdir -p ~/.local/bin
mv kubectl ~/.local/bin/kubectl
rm kubectl.sha256
cd -
```

> 你的 Mac 是 Apple Silicon，所以下载的是 `darwin/arm64` 版本。

### 步骤 3：安装 Session Manager 插件和 Helm

- **session-manager-plugin**：`aws ssm start-session` 依赖它来建立交互式会话，没有它就登录不了节点
- **Helm**：K8s 的"包管理器"（类似 apt / brew），第 10 章开始使用。Homebrew 现在装的是 Helm 4

💻 **Mac：**

```bash
brew install --cask session-manager-plugin
brew install helm
```

### 步骤 4：确认 AWS 凭证

💻 **Mac：**

```bash
aws sts get-caller-identity

```

第一条会显示你的账号 ID 和 IAM 用户（`.../user/admin`）。第二条应该是 `us-east-1`。

## ❓ 思考题

**1. 用自己的话说说，"声明式"和"命令式"有什么区别？为什么说声明式更适合管理大规模系统？**

<details>
<summary>参考答案</summary>

命令式描述"做什么"（启动 3 个容器），执行完就结束了；声明式描述"要什么状态"（始终保持 3 个容器），系统会持续把现实拉向期望。

在大规模系统里，故障是常态（机器会挂，网络会抖）。命令式需要人或脚本处理每一种异常；声明式只需要定义好终态，控制循环会自动处理"不管什么原因导致的偏离"。它还天然是**幂等**的：同一份声明提交 10 次，结果和提交 1 次一样。
</details>

**2. 如果 kube-scheduler 挂了，已经在运行的 Pod 会受影响吗？新创建的 Pod 呢？**

<details>
<summary>参考答案</summary>

已经在运行的 Pod **不受影响**。scheduler 只负责给"还没分配节点"的 Pod 挑机器，Pod 一旦被分配，后面就是 kubelet 的事了。

新创建的 Pod 会一直处于 **Pending** 状态，因为没有人给它分配节点。第 19 章我们会故意制造这种故障。
</details>

**3. 为什么所有组件都只和 apiserver 通信，而不是互相直接通信？**

<details>
<summary>参考答案</summary>

- **解耦**：每个组件只需要知道 apiserver 的地址，增删组件不影响其他组件
- **统一的安全控制**：认证、鉴权、准入校验都集中在 apiserver 一处完成
- **单一数据源**：只有 apiserver 读写 etcd，保证数据一致
- **watch 机制**：组件通过 apiserver 的 watch 接口订阅变化，有更新时立刻收到通知，不需要互相调用
</details>

**4. etcd 为什么被称为"集群的命根子"？**

<details>
<summary>参考答案</summary>

集群的所有状态都存在 etcd 里：有哪些 Deployment、Service、Secret、节点……其他组件全都是"无状态"的，挂了重启就能恢复，因为它们的数据都从 apiserver（也就是 etcd）读取。

而 etcd 的数据一旦丢失且没有备份，整个集群的配置就全没了。所以生产环境的 etcd 必须做高可用（3 或 5 个成员）和定期备份。第 11 章和第 18 章会专门练习。
</details>
